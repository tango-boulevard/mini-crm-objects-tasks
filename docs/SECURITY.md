# Архитектура безопасности

## 1. Активы

Система защищает:

- данные строительных объектов;
- содержание и назначение задач;
- историю выполнения;
- роли пользователей;
- пользовательские сессии;
- ключи и параметры инфраструктуры.

## 2. Модель угроз

Предполагается, что пользователь может:

- открыть инструменты разработчика;
- изменить JavaScript или параметры запроса;
- вызвать Supabase REST или RPC напрямую;
- подставить чужой идентификатор объекта, задачи или пользователя;
- повторить старый запрос;
- одновременно отправить несколько переходов;
- попытаться изменить системные поля;
- попытаться вставить, исправить или удалить историю.

Поэтому скрытая кнопка и клиентская валидация не считаются мерами авторизации.

## 3. Матрица доступа

| Ресурс и действие | Постановщик | Исполнитель |
|---|---:|---:|
| Читать профили исполнителей для назначения | Да | Нет, кроме собственного профиля |
| Читать объекты | Все | Только объекты со своими задачами |
| Создать объект | Да | Нет |
| Изменить объект | Да | Нет |
| Удалить пустой объект | Да | Нет |
| Читать задачи | Все | Только назначенные ему |
| Создать задачу | Да | Нет |
| Изменить поля новой задачи | Да | Нет |
| Удалить новую не начатую задачу | Да | Нет |
| Изменить статус напрямую | Нет | Нет |
| Вызвать разрешённый переход | По таблице переходов | Только для своей задачи по таблице переходов |
| Читать историю | Всю | Только историю своей задачи |
| Добавить историю напрямую | Нет | Нет |
| Изменить или удалить историю | Нет | Нет |

## 4. Защитные слои

### Ограничения схемы

Используются `NOT NULL`, внешние ключи, `RESTRICT`, перечисления и проверки непустого текста. Они защищают целостность независимо от способа записи.

### RLS

RLS включается принудительно для предметных таблиц. Политики используют `auth.uid()` и серверную роль из `profiles`. Для каждой операции создаётся минимально необходимая политика.

### Привилегированные функции

Если функция использует `SECURITY DEFINER`, она:

- имеет фиксированный безопасный `search_path`;
- полностью квалифицирует таблицы;
- проверяет `auth.uid()`;
- не принимает actor или author от клиента;
- имеет отозванный публичный `EXECUTE` и явный grant только `authenticated`;
- не предоставляет возможности произвольного SQL или выбора таблиц.

### Неизменяемая история

У `authenticated` нет прямых прав на запись истории. Начальная запись и переходы создаются только доверенными функциями. Обновление и удаление записей истории не предоставляются приложению.

## 5. Безопасность перехода

Функция перехода:

1. отклоняет анонимного пользователя;
2. нормализует комментарий;
3. получает профиль и проверяет активность;
4. читает задачу `FOR UPDATE`;
5. не различает для исполнителя чужую и несуществующую задачу в сообщении ошибки;
6. проверяет конкретную пару статусов;
7. проверяет роль и назначение;
8. требует комментарий для возврата;
9. обновляет статус с серверным временем;
10. добавляет историю с `auth.uid()`;
11. возвращает минимально необходимый результат.

Блокировка строки сериализует конкурирующие переходы одной задачи. Второй запрос увидит уже новый статус и будет проверен заново.

## 6. Защита секретов

- В `.env.example` находятся только имена переменных и безопасные примеры.
- `.env` игнорируется Git.
- Frontend использует только URL и anon key.
- `service_role`, access token Supabase CLI и пароли тестовых пользователей не коммитятся.
- Секреты деплоя задаются в панели хостинга.

## 7. Тесты безопасности

Минимальные автоматические проверки:

- исполнитель A читает свою задачу;
- исполнитель A не читает задачу B;
- исполнитель A не получает объект только с задачами B;
- исполнитель не вставляет и не редактирует объект;
- исполнитель не меняет `assignee_id`, `created_by` или `status`;
- постановщик видит все задачи;
- разрешённый переход проходит;
- переход чужой задачи отклоняется;
- переход не из текущего статуса отклоняется;
- возврат без комментария отклоняется;
- прямые insert, update и delete истории отклоняются;
- одновременные переходы не создают противоречивую историю.

## 8. Остаточные риски

- Пользователь с доступом к проекту Supabase Dashboard обладает административными возможностями вне модели приложения.
- `service_role` обходит RLS; его утечка критична и предотвращается процессом хранения секретов.
- Без отдельного аудита инфраструктуры невозможно доказать отсутствие ошибок конфигурации панели; итоговый чек-лист должен включать ручную проверку закрытой регистрации и переменных деплоя.
