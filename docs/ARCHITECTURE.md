# Архитектура мини CRM

## 1. Архитектурная цель

Приложение строится как статический React-клиент и управляемая Supabase-база. Supabase предоставляет аутентификацию, PostgreSQL, REST API и RPC. Главная граница доверия проходит в базе данных: клиент помогает пользователю, но не определяет его реальные права.

```text
Браузер
  React UI
    feature services
      Supabase JS client с anon key
        Auth
        PostgREST с RLS
        RPC transition_task_status
          PostgreSQL constraints and policies
          append only task_status_history
```

`anon` key является публичным идентификатором проекта и может находиться во фронтенде. Безопасность обеспечивают пользовательская сессия, RLS, ограничения и серверные функции. `service_role` во фронтенде отсутствует.

## 2. Компоненты

### React приложение

Отвечает за:

- маршрутизацию и экраны;
- формы и клиентскую валидацию;
- отображение только доступных действий;
- кеширование запросов;
- обработку загрузки и ошибок;
- вызов обычных запросов и контролируемых RPC.

Не отвечает за окончательное решение о доступе и допустимости перехода статуса.

### Supabase Auth

Отвечает за вход по email и паролю и выпуск пользовательской сессии. Открытая регистрация отключается. Профиль и роль создаются административно для заранее подготовленных пользователей.

### PostgreSQL и RLS

Отвечают за:

- хранение профилей, объектов, задач и истории;
- фильтрацию видимых строк;
- запрет изменения защищённых полей;
- допустимость переходов;
- атомарную запись истории;
- ссылочную целостность.

Структура сознательно проще строгой Feature-Sliced Design. `pages` собирают сценарии, `features` содержат действия пользователя, `entities` содержат запросы и представления предметных сущностей, `shared` не зависит от предметных модулей.

## 4. Потоки данных

### Чтение списка объектов

1. React Query вызывает модуль `entities/object/api`.
2. Supabase выполняет `select` с пользовательской сессией.
3. RLS возвращает все объекты постановщику или только связанные объекты исполнителю.
4. Клиент кеширует уже отфильтрованный результат.

### Создание задачи

1. Форма проверяет обязательные поля.
2. Клиент выполняет `insert` задачи без автора, даты и произвольного статуса.
3. База проверяет роль постановщика и корректность исполнителя.
4. Серверные значения устанавливают автора, дату и статус `new`.
5. База создаёт начальную запись истории.

### Смена статуса

1. UI вычисляет возможные действия для удобства отображения.
2. Пользователь вызывает `transition_task_status(task_id, target_status, comment)`.
3. Функция получает текущего пользователя через `auth.uid()`.
4. Строка задачи читается с блокировкой `FOR UPDATE`.
5. Функция проверяет роль, назначение, исходный и целевой статусы и комментарий.
6. Функция обновляет статус и добавляет историю.
7. Оба действия подтверждаются одной транзакцией либо полностью откатываются.
8. React Query инвалидирует задачу, историю и связанные списки.

## 5. Границы транзакций

- Создание задачи и начальной записи истории выполняется атомарно.
- Каждый переход статуса и его история выполняются атомарно.
- Удаление объекта проверяет отсутствие задач.
- Удаление задачи проверяет, что она всё ещё новая и не имеет рабочих переходов.

## 6. Обработка ошибок

База возвращает стабильные коды или контролируемые сообщения для ожидаемых ошибок:

- недостаточно прав;
- задача не найдена или недоступна;
- запрещённый переход;
- требуется комментарий;
- конфликт одновременного изменения;
- нарушение ссылочной целостности.

UI переводит технические ошибки в понятные пользователю сообщения и не раскрывает детали политик или SQL.

## 7. Развёртывание

- Frontend: Vercel или Netlify.
- Backend: Supabase Cloud.
- Схема: версионируемые файлы `supabase/migrations`.
- Демонстрационные данные: `supabase/seed.sql` без паролей и секретов.
- Переменные frontend: URL проекта и публичный anon key.

## 8. Осознанные ограничения

- Нет собственного backend-сервера: необходимая серверная логика реализуется PostgreSQL-функциями.
- Нет optimistic update для переходов статуса: после RPC читается подтверждённое состояние базы.
- Нет сложного глобального state manager: серверное состояние ведёт React Query, локальное остаётся в компонентах и формах.
- Нет универсального permission framework: правила предметной области выражены явно и тестируются отдельно.
