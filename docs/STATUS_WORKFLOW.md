# Переходы статусов

## 1. Автомат состояний

```text
создание
   |
   v
Новая -- исполнитель --> В работе -- исполнитель --> На проверке
                                                      |        |
                                           постановщик|        |постановщик
                                                      v        v
                                                На доработке  Принята
                                                      |
                                                      | исполнитель
                                                      v
                                                  В работе
```

## 2. Таблица правил

| Исходный статус | Целевой статус | Роль | Дополнительная проверка |
|---|---|---|---|
| `new` | `in_progress` | executor | `assignee_id = auth.uid()` |
| `in_progress` | `in_review` | executor | `assignee_id = auth.uid()` |
| `in_review` | `accepted` | manager | активный профиль |
| `in_review` | `needs_revision` | manager | непустой комментарий |
| `needs_revision` | `in_progress` | executor | `assignee_id = auth.uid()` |

Создание `new` не является пользовательским переходом через общую RPC. Оно выполняется отдельным безопасным сценарием создания задачи и также добавляет начальную историю с `from_status = NULL`.

## 3. Контракт RPC

```text
transition_task_status(
  p_task_id uuid,
  p_target_status task_status,
  p_comment text default null
) returns tasks
```

Клиент не передаёт исходный статус, пользователя или время. Исходный статус читается из заблокированной строки, а пользователь и время определяются базой.

## 4. Инварианты

- В задаче хранится текущий статус.
- Последняя запись истории после успешной транзакции соответствует текущему статусу.
- Каждая успешная смена создаёт ровно одну запись истории.
- Неуспешная смена не меняет ни задачу, ни историю.
- История упорядочивается по `changed_at`, затем по `id`.
- Комментарий возврата после trim не пуст.
- Терминальный статус `accepted` не имеет исходящих переходов.

## 5. Отображение действий

Frontend использует ту же явную таблицу переходов только для выбора кнопок и текста подтверждения. Эта таблица не заменяет серверную проверку. После ошибки или успеха клиент перечитывает задачу, поскольку состояние могло измениться в другой вкладке.
