# Спецификация мини CRM Объекты и задачи

## 1. Цель

Создать небольшую CRM для строительной компании. Постановщики управляют объектами и задачами, назначают исполнителей и проверяют результат. Исполнители работают только со своими задачами. Система должна сохранять достоверную историю статусов и обеспечивать доступ на уровне базы данных даже при прямом обращении к Supabase API.

## 2. Пользователи и роли

### Постановщик

- видит все объекты, задачи и историю;
- создаёт и редактирует объекты;
- создаёт задачи и назначает исполнителя;
- редактирует разрешённые поля задачи;
- принимает задачу или возвращает её на доработку;
- может удалять только сущности, для которых это разрешено правилами целостности.

### Исполнитель

- видит только назначенные ему задачи;
- видит объекты, к которым относятся его задачи;
- переводит новую задачу в работу;
- отправляет задачу на проверку;
- повторно берёт в работу задачу после возврата;
- видит историю доступной ему задачи;
- не может изменять бизнес-поля задачи, назначение, автора или историю.

## 3. Сущности

### Профиль пользователя

- идентификатор, совпадающий с `auth.users.id`;
- отображаемое имя;
- роль: `manager` или `executor`;
- признак активности;
- дата создания.

### Объект

- идентификатор;
- название;
- адрес;
- автор записи;
- даты создания и изменения.

### Задача

- идентификатор;
- название;
- описание;
- объект;
- назначенный исполнитель;
- статус;
- автор;
- даты создания и изменения.

### История статуса

- идентификатор;
- задача;
- исходный статус, отсутствующий при создании;
- новый статус;
- пользователь, выполнивший переход;
- дата и время;
- комментарий, обязательный при возврате на доработку.

## 4. Жизненный цикл задачи

Разрешены только следующие переходы:

| Из статуса | В статус | Кто выполняет | Дополнительное условие |
|---|---|---|---|
| Нет | Новая | Постановщик | При создании задачи |
| Новая | В работе | Назначенный исполнитель | Нет |
| В работе | На проверке | Назначенный исполнитель | Нет |
| На проверке | Принята | Постановщик | Нет |
| На проверке | На доработке | Постановщик | Непустой комментарий |
| На доработке | В работе | Назначенный исполнитель | Нет |

Любой другой переход отклоняется базой данных. Интерфейс показывает только действия, доступные текущему пользователю, но не является границей безопасности.

## 5. Экраны

### Вход

- email;
- пароль;
- понятное сообщение об ошибке;
- отсутствует открытая регистрация.

### Список объектов

- постановщик видит все объекты;
- исполнитель видит только объекты, где у него есть хотя бы одна задача;
- отображаются название и адрес;
- доступен переход в карточку объекта.

### Карточка объекта

- название и адрес;
- список видимых пользователю задач;
- статус, исполнитель и автор задачи;
- постановщик может создать задачу;
- исполнитель не видит чужие задачи этого же объекта.

### Карточка задачи

- все доступные пользователю данные задачи;
- только разрешённые текущему пользователю действия;
- форма комментария при возврате на доработку;
- хронологическая история переходов.

### Мои задачи

- доступна исполнителю;
- содержит только назначенные ему задачи;
- позволяет быстро перейти к карточке задачи;
- поддерживает фильтрацию по статусу как небольшое улучшение сильной версии.

## 6. Требования безопасности

- Все таблицы с пользовательскими данными защищены RLS.
- Роль берётся из серверной таблицы профилей, а не из переданного клиентом значения.
- Исполнитель не может прочитать или изменить чужую задачу прямым API-запросом.
- Исполнитель не получает объект, если у него нет задачи на этом объекте.
- Изменение статуса выполняет только контролируемая функция базы.
- Функция блокирует задачу на время перехода и предотвращает гонки.
- Создание записи истории происходит атомарно с изменением статуса.
- Обычные пользователи не могут вставлять, изменять или удалять историю напрямую.
- Автор, исполнитель перехода и временные метки определяются сервером.
- Открытая регистрация отключена в настройках Supabase.
- Привилегированные ключи отсутствуют во фронтенде и репозитории.

## 7. Нефункциональные требования

- Интерфейс работает на актуальных настольных и мобильных браузерах.
- Все основные экраны имеют состояния загрузки, ошибки и отсутствия данных.
- Проект собирается одной документированной командой.
- Схема базы воспроизводится миграциями из пустого проекта Supabase.
- Тестовые данные позволяют проверить обе роли и все ключевые статусы.
- Критические политики доступа и переходы покрыты автоматическими проверками.

## 8. Критерии приёмки

Сильное тестовое считается готовым, когда:

1. постановщик создаёт объект и назначает задачу исполнителю;
2. исполнитель видит эту задачу, но не видит задачу другого исполнителя;
3. разрешённая цепочка статусов проходит полностью;
4. запрещённый переход отклоняется прямым запросом к базе;
5. возврат без комментария отклоняется;
6. история содержит правильного пользователя, время и оба статуса;
7. историю невозможно изменить или удалить обычным API-клиентом;
8. миграции разворачивают схему повторяемо;
9. production build проходит успешно;
10. README, объяснение руководителю и список решений соответствуют реализации.

## 9. За пределами первой версии

- вложения;
- уведомления;
- сроки и просрочка;
- поиск по тексту;
- комментарии вне переходов статуса;
- управление организациями;
- публичная регистрация;
- расширенные роли;
- офлайн-режим.
