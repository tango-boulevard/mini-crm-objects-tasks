# Решения и допущения

Этот документ фиксирует ответы на неоднозначности исходного задания. Решения могут уточняться до начала соответствующего этапа, но изменение уже реализованного правила должно сопровождаться изменением спецификации и тестов.

## D001 Роли хранятся в профилях

**Решение:** роль хранится в таблице `profiles`, связанной с `auth.users`. Клиент не может менять роль.

**Причина:** данные JWT могут быть устаревшими или ошибочно управляться клиентом. Таблица профилей даёт одну серверную точку истины для RLS.

## D002 Исполнитель видит объект только через свои задачи

**Решение:** исполнитель видит название и адрес объекта, если на объекте существует хотя бы одна назначенная ему задача. В карточке такого объекта он всё равно видит только собственные задачи.

**Причина:** это прямо следует из задания и исключает утечку задач коллег.

## D003 Изменение статуса выполняется отдельной функцией

**Решение:** прямое обновление статуса клиентом запрещено. Используется RPC-функция `transition_task_status`.

**Причина:** функция обеспечивает атомарную проверку перехода, изменение задачи и добавление истории.

## D004 История неизменяема

**Решение:** для `task_status_history` отсутствуют пользовательские политики `INSERT`, `UPDATE` и `DELETE`. Записи создаёт только контролируемая серверная функция.

**Причина:** история должна быть доказательством, а не редактируемым журналом.

## D005 Удаление задачи с историей запрещено

**Решение:** постановщик может удалить только новую задачу, по которой ещё не было рабочих переходов. После начала работы задача сохраняется. В первой версии архивирование не реализуется.

**Причина:** физическое удаление выполненной работы противоречит достоверности истории. Это осторожное толкование неоднозначного требования об удалении задач.

**Вопрос работодателю:** если ожидается безусловное физическое удаление, правило можно заменить на архивирование без потери истории.

## D006 Удаление объекта с задачами запрещено

**Решение:** объект удаляется только при отсутствии задач.

**Причина:** каскадное удаление задач и истории опасно, а архивирование не входит в первую версию.

## D007 Переназначение ограничено

**Решение:** постановщик может сменить исполнителя только у задачи в статусе `new`. После начала работы назначение фиксируется.

**Причина:** иначе история ответственности становится неоднозначной. Расширенный процесс переназначения можно добавить отдельно.

## D008 Редактирование рабочих задач ограничено

**Решение:** постановщик может изменить название, описание и объект только в статусе `new`. Во время работы эти поля доступны только для чтения.

**Причина:** исполнитель должен завершать ту постановку, которую принял в работу.

## D009 Комментарий сохраняется только при переходе

**Решение:** комментарий является частью записи истории. Он обязателен при возврате на доработку и необязателен для остальных переходов.

**Причина:** отдельный чат и произвольные комментарии не требуются заданием.

## D010 Принятая задача терминальна

**Решение:** после статуса `accepted` переходов нет.

**Причина:** другие переходы прямо запрещены заданием. Повторное открытие является будущим расширением.

## D011 Тестовые пользователи создаются вне приложения

**Решение:** публичной регистрации и пользовательской административной панели нет. Демонстрационные аккаунты создаются через Supabase Dashboard или административный seed-процесс.

**Причина:** это соответствует требованию отключить открытую регистрацию и удерживает объём тестового.
